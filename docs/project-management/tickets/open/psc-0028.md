## Description
Implement the SQLite-backed ProfileStorage for persistent multi-week behavioral analysis. This is optional — the CLI works without SQLite, using MemoryProfileStorage by default. When the user runs with `--profile-db FILE`, SqliteProfileStorage is used instead.

**Key design decisions:**
1. SQLite is a CLI-level dependency, not a library dependency — `libble_sniffer` must compile without sqlite3
2. Conditional compilation: `USE_SQLITE` CMake option controls whether SqliteProfileStorage is built
3. Schema must support the three profile types from psc-0025/psc-0027:
   - `devices` table: DeviceId primary key, first_seen, last_seen
   - `session_profiles` table: device_id FK, start_time, end_time, duty_cycle, signal_stats, confidence, classification
   - `daily_profiles` table: device_id FK, date, session_count, total_present_time, confidence, classification
   - `longterm_profiles` table: device_id FK, start_date, end_date, day_count, confidence, classification
4. Database file created on first use with `PRAGMA journal_mode=WAL` for safe concurrent access
5. All queries use prepared statements (parameterized) — no string concatenation for SQL
6. Graceful fallback: if SQLite is not compiled in, `--profile-db` flag produces an error message

**Architecture alignment:**
- SqliteProfileStorage sits in the adapter layer (outermost dependency rule layer)
- CLI wires SqliteProfileStorage when `--profile-db` is used, MemoryProfileStorage otherwise
- PresenceAnalyzer never knows which storage backend is in use — it only depends on the ProfileStorage interface

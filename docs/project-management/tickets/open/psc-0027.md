## Acceptance Criteria

2. `MemoryProfileStorage` implementation storing profiles in `std::unordered_map`
3. `save_session()`, `save_daily()`, `save_longterm()` methods
4. `load_daily()`, `load_dailies()`, `load_longterm()` methods
5. `known_devices()` and `total_profiles()` query methods
6. No SQLite dependency — MemoryProfileStorage is the default
7. Unit tests for all CRUD operations
8. Build passes

## Description
Implement the `ProfileStorage` interface and its in-memory default implementation. This provides the persistence layer for behavioral profiles. The interface is pluggable so that `SqliteProfileStorage` can be added later without changing any business logic.

**Key design decisions:**
1. `ProfileStorage` is an abstract interface (pure virtual) — no implementation details leak
2. `MemoryProfileStorage` stores all profiles in memory using `std::unordered_map<DeviceId, ...>` keyed by device ID
3. The interface supports three profile types: `SessionProfile`, `DailyProfile`, `LongTermProfile` (defined in psc-0025)
4. Query methods: `known_devices()` returns set of DeviceIds with profiles, `total_profiles()` returns count
5. No SQLite dependency at this stage — MemoryProfileStorage is the default and only implementation
6. `SqliteProfileStorage` (psc-0028) will implement the same interface later

**Architecture alignment:**
- ProfileStorage sits in the state layer (dependency rule: inner modules never depend on outer)
- PresenceAnalyzer depends on ProfileStorage (abstraction), not MemoryProfileStorage (concrete)
- CLI wires MemoryProfileStorage by default, SqliteProfileStorage when `--profile-db` is used

## Acceptance Criteria
1. `DeviceRegistry` class exists in `include/ble_sniffer/device_registry.h`
2. `DeviceEntry` struct holds: mac, last_seen, last_rssi, last_payload, adv_type, rssi_ema, rssi_ema_initialized, inside_region, last_event_fired
3. LRU eviction with configurable capacity (default 10000)
4. `get_or_create(mac)`, `get(mac)`, `evict(mac)`, `size()`, `clear()` methods
5. `stat_view` refactored to read from `DeviceRegistry` instead of internal tracking
6. `main.cpp` creates a single `DeviceRegistry` and passes it to both `StatView` and future `DeviceEventTracker`
7. Unit tests for DeviceRegistry (LRU eviction, get/create, capacity limit)
8. Build passes

## Description
Extract the per-MAC device tracking logic from `stat_view.h` into a standalone `DeviceRegistry` class. The registry is the single source of truth for per-MAC state, shared between `--stat` display and the event engine. It must hold both device data (last_seen, rssi, payload, adv_type) and signal processing state (rssi_ema, rssi_ema_initialized, inside_region, last_event_fired). LRU eviction with configurable capacity prevents unbounded memory growth.

The `DeviceRegistry` is a key architectural module — it's the foundation for the event engine (psc-0021), presence analyzer (psc-0025), and BlePresenceAdapter (psc-0026). It must be reusable for WiFi and Zigbee (per-MAC or per-address tracking), with no BLE-specific logic.

**Key design decisions:**
1. LRU eviction policy: when capacity is reached, evict the least-recently-seen device (not LRU-accessed, to avoid scan storms evicting idle devices)
2. Thread safety: single-threaded for now (main loop only), but interface should not preclude future locking
3. DeviceEntry fields: must support both display (stat_view) and event detection (rssi_ema, inside_region, last_event_fired) use cases

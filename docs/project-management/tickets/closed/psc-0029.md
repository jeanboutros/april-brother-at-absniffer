## Description

A runtime bug was discovered when running the CLI with a device path that won't work (e.g. `/dev/cu.Bluetooth-Incoming-Port`). The program exits silently with the message "Bluetooth AT Driver cleaned up." and return code 0, giving the user no feedback that anything went wrong.

### Root Cause 1: `init()` is never called

In `src/main.cpp:102` (original, before the out-of-pipeline fix), the `ABSnifferSerialPort` is constructed but `init()` is never called before passing it to `BluetoothATDriver`. Without `init()`, the serial port file descriptor stays at -1, `is_open()` returns false, and all operations silently no-op. The driver's destructor prints "cleaned up" regardless of whether it was ever functional.

### Root Cause 2: No action flag validation

If the user provides a device path but no `-i`, `-s`, or `--stop-scan` flag, the program constructs the driver, the destructor runs (printing "cleaned up"), and exits with return code 0 — giving no feedback that nothing happened.

### Process Violation

The fix for both root causes was applied directly to the codebase without going through the pipeline. This violates the DISPATCH-ONLY rule: all changes must be routed through tickets, passports, and the validation pipeline. This ticket exists to:

1. Formally track the bug and the fix that was already applied
2. Ensure the fix is reviewed through the proper pipeline (Phases A, B, C, C4)
3. Serve as a process correction record
